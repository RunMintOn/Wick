# 验证是否有效

## 断言文件存在，不代表检查已执行

**已观察：HyperFrames 0.8.216。** 检查根工程时，放在 `compositions/` 内、与子合成同名的 `.motion.json` 没有启用运动验证；报告仍为 `ok: true`，但 `motion.enabled: false`、`motion.samples: 0`。改用根目录 `index.motion.json` 后，报告显示验证启用并实际采样。

已有 CLI Skill 解释了报告结构；这里补充的是断言文件被忽略时的确认与处理：

1. 存在自定义运动断言时，核对报告的 `motion.enabled`、`motion.samples`，以及实际读取的 `specPath`。字段随版本变化时，以当前文档和报告为准。
2. 确认检查命令针对哪个工程或合成。若当前版本确实没有读取子合成断言，可将所需断言放到根目录的 `index.motion.json`。
3. 移动断言时同步调整时间和选择器。子合成局部时间不是整片时间：例如挂载在第 5 秒的场景，其局部 `bySec: 4.6` 对应整片 `bySec: 9.6`；选择器需命中实际组装后的元素。
4. 重新检查，确认目标断言已被读取、采样且通过。

**完成标准：** 目标检查实际执行，并有对应结果；文件存在或顶层 `ok` 为真都不足以证明这一点。

若新版已经正常发现子合成断言，就保留原位置，不做兼容迁移。

## 拆段后的同名元素使断言产生歧义

**已观察：HyperFrames 0.8.216。** 同一子合成挂载两次后，`#title` 等内部选择器匹配多份元素，运动检查报 `motion_selector_ambiguous`，对应断言未执行。可视编辑器拆段后尤其容易出现。

保留实例及其源偏移，把断言限定到实际要检查的宿主，例如 `#scene-a #title`。`before` 的两个选择器也分别限定范围。若目标本来跨实例，就明确各自宿主；不要仅为让检查通过而选第一项、删掉后段或批量重命名共享源码。

**完成标准：** 每个断言目标唯一，歧义消失，断言实际执行；相关实例的播放顺序仍正确。

## 已结束场景被跨全片的 keepsMoving 判成冻结

**已观察：HyperFrames 0.8.216。** 片头隐藏后，`keepsMoving` 仍把它到后续场景之间的不可见区间计为静止，报 `motion_frozen`。

将报告的冻结区间与宿主的有效展示区间及运行时隐藏状态对照。若冻结发生在目标已退出之后，应调整检查范围，而不是让隐藏场景继续动画。若当前工具无法限定有效区间，可以检查该区间的帧序列，并保留其他有效断言；明确该项没有自动验证，不能只删除断言再宣称全部运动已通过。

**完成标准：** 实际展示区间内的运动有证据；隐藏区间不再被当成可见冻结。目标可见时仍冻结的情况继续按播放故障排查。

## 未来场景的素材尚未加载，被误报为播放故障

**已观察：HyperFrames 0.8.216 的预览按需加载场景素材。** 播放到第 26 秒时，尚未进入的片尾场景里，图标可以仍为 `naturalWidth: 0`；进入片尾后正常加载。对整个 DOM 的图片做即时检查会误报。

按时间范围验证素材，而不是扫描所有已挂载节点：

1. 从时间线确定当前需要显示的场景和素材。
2. 对当前应显示的图片检查资源请求、解码和实际画面。浏览器的可见性 API 可以辅助筛选，但不能替代时间线判断：不透明遮挡层也可能盖住缺失素材。
3. 对未来素材继续推进到其展示时间再验证。此时仍为空白、加载失败或未解码，才是实际故障。

**完成标准：** 相关素材在应显示的时间点已加载、解码并出现在画面中。仅排除未来场景，不能把“当前应显示却没显示”的素材也过滤掉。

## 本地渲染成功，不证明网页导出成功

这是验证边界，不是网页导出故障记录。CLI `render` 成功和 MP4 可解码，只证明实际执行过的本地导出路径；预览网页能播放也不证明其导出按钮已走通。

交付时按原 review 流程说明实际路径和证据。未操作网页导出时标记未验证，既不打包票，也不推断它必然失败；可提供已验证的同工程 CLI 渲染路径。音频信号测量、抽帧核对同样不能写成“已试听、已按正常速度完整观看”。

**完成标准：** 结论不超出实际执行过的路径。只有相应网页导出被执行、输出得到核对后，才能确认该路径通过。
