# 接管已运行的本机服务

接管包括停止目标旧实例并用登记后的命令重新启动。先确认用户授权了这个服务的接管；安装、版本升级、数据迁移和删除数据分别按实际请求处理。

## 切换前

- 用监听端口定位 PID，再读取完整启动命令，确认它确实是目标服务。
- 保留原版本和启动参数，避免在接管时顺便升级程序或改变监听范围。
- 查明数据目录及其内容。用户确认是空实例时，直接准备持久数据目录，保留旧目录即可。
- 有现有数据且需要搬移时，先确定可恢复的备份或一致复制方法。保留旧目录，确认复制目标不会覆盖另一份数据。
- 准备好固定位置的可执行程序和配置。先关闭该登记的自启，完成校验与应用；切换前不启动会争抢同一端口的新实例。

## 切换

1. 优先正常停止已确认的旧 PID。停止命令返回不等于进程已退出；等待原 PID 消失，并确认监听端口已释放。
2. 需要离线复制数据时，确认所有写入者已退出，再复制和检查。空实例跳过数据搬移。
3. 前面的步骤全部成功后，才启动登记后的服务。串联命令使用 `&&` 或脚本的失败退出机制，避免复制失败后仍然启动一个意外的新数据库。
4. 检查目标服务状态、唯一监听实例、实际访问结果以及日志。

## SQLite 与 WAL

SQLite 的有效数据可能仍在 `-wal` 文件中。运行中复制单个 `.db` 不能证明数据完整。可以使用数据库的一致备份能力，或在进程正常退出、检查点完成后复制整个数据目录。

Process Compose 的 stop 返回时，应用可能仍在做退出清理。先等待 PID 完全退出，再做离线检查。

已关闭的 WAL 数据库使用普通只读连接时，在本机曾出现打开失败。`immutable=1` 可以用于已停止且不再修改的完整数据库检查；它忽略 WAL，因此只能在确认写入结束、有效内容已经进入主数据库时使用。运行中或还有未合并 WAL 数据时，使用正常的一致读取/备份方式。

## 失败处理

停止、复制或校验失败时，保留原目录和当前证据，停止后续启动步骤。已意外生成新数据目录时，先确认其内容；保留它，避免为了完成接管而覆盖用户刚写入的数据。

修复后重新检查端口所有者再启动，避免两个实例争抢端口。回退使用原程序和原数据时，先确认新实例已停止；有新写入的数据时，应明确指出两份数据的区别。
